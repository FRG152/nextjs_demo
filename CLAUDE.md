## Commands

- `npm run dev` — start the dev server (Turbopack, on by default in Next.js 16)
- `npm run build` — production build (Turbopack by default)
- `npm run start` — run the production build
- `npm run lint` — run ESLint directly (flat config in `eslint.config.mjs`; the `next lint` command was removed in Next.js 16)

There is no test runner configured in this project.

## Architecture

This is a Next.js 16 App Router learning project exploring App Router conventions: route groups, layouts, dynamic routes, server vs. client components, and route handlers. Next.js 16 has significant breaking changes vs. earlier/training-data versions — the `AGENTS.md` import above points at `node_modules/next/dist/docs/` for version-matched docs; consult it before writing routing, caching, or data-fetching code.

- Two independent route groups under `app/`, each with its own layout (no shared page/layout UI between them — small client utilities like `ThemeToggle` are an intentional exception, see below):
  - `app/(root)/` — public pages (`/`, `/about`), with `app/(root)/error.tsx` as the error boundary for that segment.
  - `app/(dashboard)/dashboard/` — `/dashboard/users`, `/dashboard/users/[id]` (dynamic segment), `/dashboard/analytics`.
- `app/api/books/route.ts` is a Route Handler (`GET`/`POST`) backed by the in-memory array in `app/api/db.ts`. There is no persistence layer — POSTed books only mutate the in-process array and reset on server restart.
- Dynamic APIs follow the Next.js 16 async-only model: route `params` are a `Promise` that must be `await`ed (see `app/(dashboard)/dashboard/users/[id]/page.tsx`), and `error.tsx` receives a `retry()` function (the `reset()` prop is legacy/discouraged) to re-fetch and re-render the failed segment (see `app/(root)/error.tsx`).
- Layout/page prop types like `LayoutProps<"/">` are Next's auto-generated route-aware type helpers (`PageProps`, `LayoutProps`, `RouteContext`) — they're globally available without imports and regenerated by `next dev`/`next build`.
- `components/hello.tsx` is the project's `'use client'` reference component; everything else is a server component by default, so treat client-directive placement as intentional when reading existing pages.
- React Compiler is enabled (`reactCompiler: true` in `next.config.ts`), so manual `useMemo`/`useCallback` memoization is unnecessary.
- Styling is Tailwind CSS v4, imported via `@import "tailwindcss"` in `app/globals.css`, with theme tokens declared through `@theme inline`.
- Dark mode uses `next-themes`, wired up in `app/layout.tsx` (`ThemeProvider` from `components/theme-provider.tsx`, `attribute="class"`, `defaultTheme="system"`, `<html suppressHydrationWarning>`). Tailwind's `dark:` variant is remapped from `prefers-color-scheme` to the `.dark` class via `@custom-variant dark (&:where(.dark, .dark *));` in `app/globals.css`. `components/theme-toggle.tsx` detects client mount with `useSyncExternalStore` rather than `useEffect`+`useState`, to avoid tripping the `react-hooks/set-state-in-effect` lint rule.
